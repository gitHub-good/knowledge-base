# 📥 01 · 需求管理

> 闭环起点。需求管理的目标不是"记下所有想法"，而是**把模糊的诉求变成可开发、可验收、可排序的需求条目**。需求不清是后期一切返工的最大来源。

## 📍 阶段定位

- 📥 **上游输入**：原始诉求（业务方、用户反馈、自己观察、线上问题、复盘改进项）。
- 📤 **下游输出**：冻结的需求条目（含验收标准），作为 [02 设计架构](/project-development/02-design/index.md) 的输入。

## 🗂️ 一、需求分类

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 功能需求 | 新能力 | 退保单支持部分退款 |
| 优化需求 | 体验/性能改进 | 列表页加载从 3s 降到 1s |
| 缺陷需求 | 线上问题 | 保函编号重复 |
| 技术需求 | 技术债/基建 | 升级框架版本、补测试、还债 |

> 四类需求**统一进同一个需求池**管理，只是标签不同。技术债不排期 = 永远还不完。

## 📝 二、需求条目标准格式（用户故事）

```
作为 <角色>，
我想要 <功能/能力>，
以便 <获得的价值>。

验收标准：
- 场景 1：Given <前置条件> When <操作> Then <期望结果>
- 场景 2：Given ... When ... Then ...
```

写法要求：
1. **用户故事三段式**：角色 → 能力 → 价值。写不出"价值"，说明还没想清楚为什么做。
2. **验收标准用 Given/When/Then**：这组标准会直接转化为 [04 测试范围矩阵](/project-development/04-testing/index.md#test-matrix) 里的测试用例——这是闭环的第一处咬合。
3. **INVEST 自检**：
   - Independent（尽量独立，不与其他故事耦合）
   - Negotiable（可协商的，不是死合同）
   - Valuable（对用户/业务有价值）
   - Estimable（可估时——估不了说明信息不足，先调研）
   - Small（小——建议拆到 ≤2 人天；拆不动的大需求先出 Spike 调研）
   - Testable（可测试——验收标准写出来就能测）

## ⚖️ 三、优先级排序

两套最常用的方法，按场景选用：

**MoSCoW（快速粗排）**
- Must have：没有就不上线
- Should have：很重要，可延后一版
- Could have：锦上添花
- Won't have：本次明确不做（写下来，防止反复讨论）

**RICE（精细比较）**

```
RICE 分数 = (Reach 触达人数 × Impact 影响程度 × Confidence 信心) / Effort 工作量
```

| 参数 | 取值参考 |
| --- | --- |
| Reach | 一个迭代周期内影响多少人/多少次 |
| Impact | 3= massive，2=high，1=medium，0.5=low，0.25=minimal |
| Confidence | 100%（有数据）、80%（有依据的推测）、50%（拍脑袋） |
| Effort | 人月/人天，越小越优先 |

## 🗃️ 四、需求池管理

- **唯一需求池**：所有需求集中一处（本仓 [backlog.md](/project-development/01-requirements/backlog.md) 由 `python tools/req.py` 管理，开发项目放 `<项目仓库>/docs/01-需求/`），禁止散落在聊天记录和脑子里。
- **状态机**：`待评审 → 已排期 → 开发中 → 已提测 → 已发布 → 已关闭 / 已拒绝（留档）`。
- **需求评审要点**（排期前过一遍）：
  - [ ] 解决什么问题？不做的代价是什么？
  - [ ] 验收标准是否可测？
  - [ ] 依赖哪些系统/第三方？风险在哪？
  - [ ] 规模是否 ≤2 人天？否则先拆分。
- **变更控制**：已排期需求要变更，必须重新评估影响面并同步所有相关方——"悄悄改需求"是返工之首因。

## 📋 五、轻量 PRD 模板

```markdown
# 需求：<需求名称>
- 编号：REQ-YYYYMMDD-序号
- 类型：功能 / 优化 / 缺陷 / 技术
- 优先级：Must / Should / Could（或 RICE 分数）
- 来源：业务方 / 线上问题 / 复盘改进项编号

## 📌 背景与问题
（现在是什么状况，痛点是什么，最好有数据）

## 🎯 目标
（做完后达到什么状态；可量化则量化）

## 📝 用户故事与验收标准
（按上文格式列出）

## 🗂️ 范围
- 本期做：
- 本期不做：

## ⚠️ 依赖与风险
（上下游系统、第三方、潜在风险及对策）
```

## ✅ 阶段检查清单（DoD）

- [ ] 每条需求有编号、类型、优先级、来源
- [ ] 用户故事三段式完整，价值说得清
- [ ] 验收标准用 Given/When/Then 写出，可直接转测试用例
- [ ] 已通过 INVEST 自检，粒度 ≤2 人天
- [ ] 依赖与风险已识别，有对策
- [ ] 需求已冻结并同步相关方 → 进入 [02 设计架构](/project-development/02-design/index.md)
