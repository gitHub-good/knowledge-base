# 🗺️ 00 · 闭环流程总览

> 闭环 = 每个阶段有**明确的输入、活动、输出和质量门禁**，任何问题都能沿链条追溯回源头，所有改进最终经待办项回流需求池。本文是五个阶段的总纲。

<a id="stage-map"></a>

## 🗺️ 一、五阶段全景

```
 01 📥 需求管理      明确"做什么、为什么、做到什么程度算完成"
      ↓ 产出：冻结的需求（含验收标准）
 02 📐 设计架构      把需求翻译成方案：架构、接口、数据、选型
      ↓ 产出：评审通过的技术方案 + ADR
 03 ✍️ 编码规范      按规范实现，提交历史可读可回溯
      ↓ 产出：通过 lint + 自测的代码分支
 04 🧪 测试规范      用分层测试证明功能正确、边界安全
      ↓ 产出：测试报告（用例通过、覆盖率达标）
 05 👀 代码评审      第二双眼睛守住正确性、可读性、一致性
      ↺ 产出：评审通过并合入主干 —— 链路收口

 06 📌 待办项（横切） 问题/改进项随手记单文件，状态自动流转；
      ↺ 改进项转需求池，开启下一轮迭代 —— 闭环完成
```

<a id="gating-matrix"></a>

## 🚦 二、准入 / 准出矩阵（质量门禁）

> 原则：**上一阶段的"准出"就是下一阶段的"准入"**；准出不达标，工作不流入下一阶段。

| 阶段 | 准入条件（DoR） | 准出条件（DoD） |
| --- | --- | --- |
| 01 📥 需求管理 | 有原始诉求或问题背景 | 需求有明确验收标准、优先级、负责人，进入排期 |
| 02 📐 设计架构 | 需求已冻结，验收标准清晰 | 技术方案评审通过，关键决策均已记录 ADR |
| 03 ✍️ 编码规范 | 方案已定，任务已拆解到 ≤2 天粒度 | 代码符合规范，lint 0 error，本地自测通过 |
| 04 🧪 测试规范 | 提测单 + 自测报告齐全 | 用例全部执行，新增代码覆盖率达标，无 P0/P1 遗留 |
| 05 👀 代码评审 | PR 小而聚焦（建议 ≤400 行），描述完整 | 评审意见全部 resolved，至少 1 人 approve |
| 06 📌 待办项 | 一件事值得跟踪（问题/改进/想法） | 有完成标准与状态；完成时自动记完成日期并刷新汇总 |

<a id="feedback-loops"></a>

## 🔁 三、两条反馈回路（闭环的灵魂）

<a id="reject-loop"></a>

### ⚡ ① 打回环：缺陷与评审意见（小时级）

```
04 测试发现缺陷 → 缺陷单（P0~P3 定级）→ 回到 03 编码修复（先补复现用例）
05 评审提出意见 → 逐条回应修改 → blocker 清零才允许合入
```

要点：
- **修复先补测试**：每个缺陷修复必须先写复现用例（修前红、修后绿），防止二刷。
- 线上紧急问题走最短路径：最小修复 + 精简评审 + 修完必合回主干，并补登一条待办跟进根因。

<a id="improve-loop"></a>

### ♻️ ② 改进环：问题与改进项回流（迭代级）

```
任何阶段发现问题/产生改进想法 → 登记 06 待办项（编号 TB-xxx，状态自动流转）
    → 有价值的转进 01 需求池（标来源=待办编号）
    → 按 RICE 排优先级 → 随后续迭代落地 → 在待办项里关闭并留档
```

要点：
- 改进项**必须和需求一样管理**（有编号、状态、完成标准），否则改进只是聊天。
- 每条改进项要能回答：**"怎么验证它生效了？"**

## 📅 四、节奏建议（可套用 Scrum 双周迭代）

| 时点 | 动作 | 对应阶段 |
| --- | --- | --- |
| 迭代前 | 需求梳理会：需求池排序、估时、领任务 | 01 |
| 迭代首日 | 技术方案评审（大需求才开评审会，小需求文档异步评审） | 02 |
| 每日 | 站会 10 分钟：昨天/今天/阻塞 | 03~05 |
| 迭代内 | 随开发随提 PR，保持小步快跑 | 03~05 |
| 迭代尾 | 提测 → 回归 → 评审合入 | 04~05 |
| 随时 | 问题/改进项随手记待办；迭代末盘点待办项，该转需求的转需求 | 06 |

## 👥 五、角色说明（单人项目同样适用）

| 角色 | 团队场景 | 单人场景 |
| --- | --- | --- |
| 需求方（PO） | 产品经理 | 自己以"用户视角"写需求 |
| 开发 | 工程师 | 自己（严格执行规范兜底） |
| 测试 | QA / 测试工程师 | 自己写自动化测试代替人工回归 |
| 评审人 | 同事 | **隔天自评**：睡一觉后 review 自己的 diff，效果接近他人评审 |

> 单人场景的现代解法：把产品经理 / 架构设计师 / 开发工程师 / 测试工程师四个角色交给子智能体，按交接物契约协作——见 [10-虚拟团队](/project-development/10-virtual-team/index.md)。
