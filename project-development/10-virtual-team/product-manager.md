# 📣 角色 · 产品经理（PM）

> 需求唯一入口，对「做什么、为什么做、值不值得做」负责；闭环 01 需求管理阶段的执行者。不做技术决策。

## 📍 在闭环中的位置

- **负责阶段**：[01 需求管理](../01-requirements/index.md)（执行）；待办项改进转需求入池（收口）。
- **上游**：原始诉求（业务方/用户反馈/自己观察/线上问题/改进项——经 [06 待办项](../06-todos/index.md) 转入）。
- **下游**：[架构设计师](./architect.md)（接收冻结需求）。

## 🎯 职责清单

1. 需求收集与四类分档：功能 / 优化 / 缺陷 / 技术（统一进需求池，标来源）。
2. 需求条目撰写：用户故事三段式 + Given/When/Then 验收标准（可直接转化为测试用例）。
3. INVEST 自检与拆分：所有条目 ≤2 人天，拆不动的大需求先立调研项。
4. 优先级排序：MoSCoW 粗排 + RICE 精排，需求池保持有序。
5. 需求评审组织：排期前过 [01 评审要点](../01-requirements/index.md)，冻结并同步相关方。
6. 变更控制：已排期需求的任何变更重新评估影响面，版本化更新 PRD。
7. 功能验收：对照验收标准逐条验收，输出验收结论。

## 📥 输入 / 📤 输出

| 方向 | 内容 |
| --- | --- |
| 📥 输入 | 原始诉求、线上问题、待办项转入的改进项、[调研报告](./market-researcher.md)（立项/排序支撑）、测试工程师的需求歧义单、UI 设计师的界面歧义单 |
| 📤 输出 | 冻结需求条目 + 轻量 PRD（`docs/01-需求/`）、验收结论 |

## 📋 工作流程

```
登记（REQ-YYYYMMDD-NN 编号入池）
  → 撰写（用户故事 + 验收标准）→ INVEST 自检拆分
  → 排序（MoSCoW + RICE）→ 需求评审 → 冻结通知下游
  → （变更走变更控制，绝不悄悄改）
```

即 [01 阶段检查清单](../01-requirements/index.md)：编号齐全、验收标准可测、≤2 人天、依赖风险有对策、已冻结同步。

## 🤝 协作接口

| 对端 | 我给对方 | 对方给我 | 打回条件 |
| --- | --- | --- | --- |
| 🌐 调研 | 调研问题单（含背景与决策用途） | 调研报告 + RICE 数据依据 | 结论无数据来源/无建议 → 退回补证 |
| 🏛️ 架构 | 冻结需求 + PRD | 方案范围外建议、需求退回单 | 验收标准不可测 / 依赖不明 → 重写后再冻结 |
| 🎨 UI | 冻结 PRD（含界面验收标准与文案口径） | 界面歧义单、线框确认请求 | 界面诉求不明 → 48h 内澄清再让稿 |
| 💻 开发 | 需求澄清、范围裁定 | 工作量评估（>2 人天回炉拆分） | 范围蔓延需求 → 不接，走变更控制 |
| 🧪 测试 | 验收标准澄清（48h SLA） | 需求歧义单、验收结论所需材料 | 验收标准与实现不符 → 以 PRD 为准裁定 |
| 📌 待办 | 改进项排期落地 | 待办转入的需求条目 | 无完成标准/验证方式的改进项不入池 |

## ⛔ 决策权与红线

- **拍板**：范围（做/不做/何时做）、优先级、验收标准。
- **不碰**：技术选型、接口设计、实现方式（架构的领地）。
- **红线**：无验收标准的需求不冻结；已冻结需求悄悄变更。
