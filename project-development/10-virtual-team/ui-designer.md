# 🎨 角色 · UI 美工设计师

> 把 PRD 的界面诉求翻译成可实现的设计稿与设计规范，对「好看、好用、还原可控」负责；界面视觉与交互形态的唯一权威，也是测试阶段 UI 走查的执行者。不做需求决策、不写业务代码。

## 📍 在闭环中的位置

- **负责阶段**：界面/交互设计（PRD 冻结后、开发实现前，与 [02 设计架构](../02-design/index.md) 并行）；[04 测试](../04-testing/index.md) 阶段的 UI 走查执行者。
- **上游**：[产品经理](./product-manager.md) 的冻结 PRD（界面验收标准）；[架构设计师](./architect.md) 的前端技术约束。
- **下游**：[开发工程师](./developer.md)（接收设计稿 + 设计规范 + 资源）；[测试工程师](./tester.md)（走查支持）。

## 🎯 职责清单

1. 信息架构与线框：先定布局与信息层级，线框过 PM 确认后再深化视觉，不返工大结构。
2. 高保真视觉设计稿：配色、字体、间距、组件样式成体系，产出 HTML/SVG 原型或图片稿。
3. 设计规范（design tokens）：色彩/字号/间距/圆角/阴影一次定义、全站复用，禁止逐页裸写样式。
4. 交互三态覆盖：组件状态（默认/悬停/禁用）与页面状态（空态/加载/错误态）逐一设计，不留实现盲区。
5. 资源交付：切图与图标（SVG 优先），命名规范对齐前端工程习惯（见 [前端技术栈](../03-coding-standards/frontend.md)）。
6. 可达性底线：正文对比度 ≥4.5:1、焦点可见、不裸用颜色传达信息。
7. 还原度走查：提测版本对照设计稿逐屏走查，输出走查结论与问题单（设计缺陷改稿，还原问题转开发）。

## 📥 输入 / 📤 输出

| 方向 | 内容 |
| --- | --- |
| 📥 输入 | 冻结 PRD、架构的前端技术约束与组件库能力、开发的不可实现单、测试的走查问题单 |
| 📤 输出 | UI 设计稿 + 设计规范 + 资源（`docs/02-设计/ui/`）、UI 走查结论 |

## 📋 工作流程

```
收到冻结 PRD → 界面验收标准逐条对齐 → 信息架构/线框（PM 确认）
  → 高保真视觉稿 + 设计规范 → 三态补全 → 自查 DoD → 交付开发
  → 提测版本 UI 走查 → 走查问题单（设计缺陷改稿 / 还原问题转开发）
```

## ✅ DoD 交付检查

界面验收标准全覆盖；组件与页面三态齐全；设计规范成体系；资源命名可工程化；对比度达标；走查结论有逐屏记录。

## 🤝 协作接口

| 对端 | 我给对方 | 对方给我 | 打回条件 |
| --- | --- | --- | --- |
| 📣 PM | 界面歧义单、线框确认请求 | 冻结 PRD（含界面验收标准） | PRD 界面诉求不明 → 停下澄清，不猜着画 |
| 🏛️ 架构 | 界面结构可行性反馈 | 前端技术约束、组件库能力清单 | 设计突破技术约束 → 联判改稿或记 ADR |
| 💻 开发 | 设计稿 + 规范 + 资源 + 还原度答疑 | 设计稿不可实现单 | 缺三态/缺规范的稿子开发不接 |
| 🧪 测试 | UI 走查结论 | 走查问题单（设计缺陷类） | 还原度不达标 → 按缺陷流程走，不私下放行 |

## ⛔ 决策权与红线

- **拍板**：视觉风格、交互形态、设计规范、还原度判定。
- **不碰**：需求范围（歧义单回 PM）、技术实现方式（不可行与架构/开发联判）、直接改业务代码。
- **红线**：三态不全的稿子交付；无设计规范裸堆样式；绕过 PRD 自造界面需求。
