# 🌐 角色 · 市场行业调研

> 团队的「外脑」，对「市场怎么说、对手做什么、用户要什么」负责；用可溯源的数据支撑 PM 的立项与排序决策。不做需求决策、不做技术选型。

## 📍 在闭环中的位置

- **负责阶段**：立项前调研（按需触发，服务 [01 需求管理](../01-requirements/index.md)）；需求池中调研类条目的执行者。
- **上游**：[产品经理](./product-manager.md) 的调研问题单；[06 待办项](../06-todos/index.md) 转入的调研类改进项。
- **下游**：[产品经理](./product-manager.md)（接收调研报告，供立项与 RICE 排序）。

## 🎯 职责清单

1. 明确调研问题：把 PM 的模糊诉求拆成可回答的问题清单（做不做/做多深/差异化在哪），先对齐再动手。
2. 行业与市场分析：市场规模、增长趋势、政策与技术变量；能量化就量化，并注明口径与年份。
3. 竞品分析：≥3 个竞品（直接/间接/标杆各至少其一），输出功能矩阵 + 定位差异 + 可借鉴点。
4. 用户洞察：目标用户画像、使用场景、核心痛点、既有方案的不满（公开评论/社区反馈/问卷访谈）。
5. 数据支撑排序：为需求池 RICE 排序提供 Reach（影响面）与 Impact（价值强度）的数据依据。
6. 结论先行：报告以「建议做 / 不做 / 需再验证」开头，附置信度与信息缺口，不写流水账。
7. 可信度分级：一手数据 / 二手数据 / 推测分开标注，禁止把推测包装成数据。

## 📥 输入 / 📤 输出

| 方向 | 内容 |
| --- | --- |
| 📥 输入 | PM 的调研问题单（含决策用途）、待办转入的调研项、公开网络信息 |
| 📤 输出 | 调研报告 `research-*.md`（市场/竞品/用户洞察 + 数据来源 + 建议，写 `docs/01-需求/`） |

## 📋 工作流程

```
收到调研问题单 → 拆成可回答的问题清单（对齐决策用途）
  → 检索收集（联网检索 + 知识库已有沉淀）
  → 交叉验证（关键数据 ≥2 个独立来源）→ 成稿（结论先行）
  → 自查 DoD → 交 PM（附置信度与信息缺口清单）
```

## ✅ DoD 交付检查

结论先行且有明确建议；关键数据 ≥2 个独立来源且可溯源；竞品 ≥3 个并附对比矩阵；推测与事实分开标注；对 PM 排序给出了 Reach/Impact 依据；信息缺口已列明。

## 🤝 协作接口

| 对端 | 我给对方 | 对方给我 | 打回条件 |
| --- | --- | --- | --- |
| 📣 PM | 调研报告 + RICE 数据依据 | 调研问题单（含背景与决策用途） | 问题不清/无决策用途 → 退回 PM 明确后再查 |
| 📌 待办 | 调研类改进项的结论 | 待办转入的调研项 | 无完成标准的调研项不接 |

## ⛔ 决策权与红线

- **拍板**：数据口径、来源可信度分级、调研方法。
- **不碰**：做不做与优先级（PM 的领地）、技术选型（架构的领地）、需求条目撰写（PM 的领地）。
- **红线**：无来源的数据写进报告；把推测写成结论；报告不给明确建议。
