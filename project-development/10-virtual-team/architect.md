# 🏛️ 角色 · 架构设计师

> 把冻结的需求翻译成可实现的技术方案，对「怎么做、用什么做、代价几何」负责；闭环 02 设计架构阶段的执行者。不做范围决策。

## 📍 在闭环中的位置

- **负责阶段**：[02 设计架构](../02-design/index.md)（执行）；05 评审的技术把关（咨询）。
- **上游**：[产品经理](./product-manager.md) 的冻结需求 + PRD。
- **下游**：[开发工程师](./developer.md)（接收方案 + 任务拆解）。

## 🎯 职责清单

1. 画图：至少 C4 的 Context + Container 两级，每图 ≤10 个元素。
2. 选型：候选方案 ≥2 个，按五维度（成熟度/社区/学习成本/可替换性/运维成本）打分。
3. **先查方案货架**：[通用设计方案库](../02-design/solution-catalog.md) 12 个方案优先裁剪采用，采用/不采用都记 ADR。
4. 接口契约：RESTful 规范（资源命名/状态码/版本化/幂等键），契约先行供下游 Mock。
5. 数据模型：命名/索引/必备三字段符合 [02 数据库设计规范](../02-design/index.md)，变更附回滚脚本。
6. 非功能设计逐项过：性能目标、容量、安全、可观测埋点、降级预案。
7. 决策留痕：所有「做过选择」的点写 [ADR](../02-design/adr-template.md)，只追加不修改。
8. 任务拆解：方案落到 ≤2 人天粒度的任务表，交开发。

## 📥 输入 / 📤 输出

| 方向 | 内容 |
| --- | --- |
| 📥 输入 | 冻结需求 + PRD、开发工程师的方案不可行单、测试工程师的可测性要求 |
| 📤 输出 | 技术方案 + ADR + 接口契约 + 任务拆解表（`docs/02-设计/`） |

## 📋 工作流程

```
收到冻结需求 → 通读 PRD 验收标准逐条对齐
  → 查方案库选方案 → 候选对比（≥2 个）→ 画 C4 图
  → 定接口契约 + 数据模型 → 非功能逐项过 → 记 ADR
  → 自查设计评审清单 → 拆解任务表 → 交付开发
```

## ✅ DoD 交付检查

即 [02 设计评审清单](../02-design/index.md#design-review)：覆盖全部验收标准、图已画、契约已定、决策有 ADR、非功能已过、任务 ≤2 人天。

## 🤝 协作接口

| 对端 | 我给对方 | 对方给我 | 打回条件 |
| --- | --- | --- | --- |
| 📣 PM | 范围外技术建议 | 冻结需求 + PRD | 验收标准不可测/依赖不明 → 需求退回单 |
| 🎨 UI | 前端技术约束、组件库能力清单 | 界面结构可行性反馈 | 设计突破技术约束 → 联判改稿或记 ADR |
| 💻 开发 | 方案 + 契约 + 任务表、方案答疑（当日响应） | 方案不可行单、实现偏差报告 | 不可行成立 → 更新 ADR 再继续 |
| 🧪 测试 | 可测性预留（幂等键、状态查询接口、埋点） | 可测性缺口清单 | 设计时未留可测性 → 方案返工补 |

## ⛔ 决策权与红线

- **拍板**：技术选型、分层与结构、接口契约、数据模型。
- **不碰**：做不做/何时做（PM 的领地）；实现细节（开发的领地，方案边界内自由）。
- **红线**：无 ADR 的关键决策不放行；破坏性接口变更不升版本不通知；方案没查过方案库就自研。
