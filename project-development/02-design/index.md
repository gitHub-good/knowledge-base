# 📐 02 · 设计架构

> 把冻结的需求翻译成可实现的技术方案。核心产出三件套：**架构图、接口契约、数据模型**；所有关键决策用 ADR 留痕——半年后还能回答"当初为什么这么选"。

## 📍 阶段定位

- 📥 **上游输入**：[01 需求管理](../01-requirements/index.md) 冻结的需求（含验收标准）。
- 📤 **下游输出**：评审通过的技术方案 + ADR 记录，作为 [03 编码规范](../03-coding-standards/index.md) 阶段任务拆解的依据。

## 🧱 一、分层架构（最通用的默认骨架）

经典四层架构（结合 DDD 分层思想），新项目默认从这里开始：

```
┌─────────────────────────────────┐
│  接入层 Controller/API/前端页面   │  参数校验、协议转换、鉴权
├─────────────────────────────────┤
│  应用层 Service/用例编排          │  事务边界、流程编排，不写业务规则
├─────────────────────────────────┤
│  领域层 Domain/核心业务           │  实体、业务规则、领域服务（最稳定的部分）
├─────────────────────────────────┤
│  基础设施层 Repository/中间件     │  数据库、缓存、MQ、第三方调用
└─────────────────────────────────┘
依赖方向：上层依赖下层；领域层不依赖任何层（依赖倒置）
```

分层铁律：
1. **依赖只能向下**，禁止循环依赖、禁止跨层调用（Controller 不直接摸数据库）。
2. **领域层保持纯净**：不 import 框架/中间件类型，保证核心业务可单测、可移植。
3. **一个类的理由只有一个**：Controller 薄、Domain 厚，业务逻辑禁止写在 Controller 里。

## 🖼️ 二、画图：C4 模型（从粗到细四层）

| 层级 | 回答的问题 | 何时画 |
| --- | --- | --- |
| Context 系统上下文 | 系统和谁交互（用户/外部系统）？ | 必画 |
| Container 容器 | 系统由哪些进程/服务/存储组成？ | 必画 |
| Component 组件 | 单个服务内部有哪些模块？ | 核心服务画 |
| Code 代码 | 类/函数级别结构 | 一般用代码自表达，不必画 |

> 原则：**图是给"半年后的自己"看的**，每张图控制在 10 个元素以内。

## ⚖️ 三、技术选型评估

> 没有特殊诉求时，先取 [个人技术栈基线](../03-coding-standards/index.md) 的默认选型，再按本节方法评估偏离项——偏离默认的决策记 ADR。

对候选技术按五个维度打分（1-5），留档进 ADR：

| 维度 | 关键问题 |
| --- | --- |
| 成熟度 | 版本是否稳定？生产案例多不多？ |
| 社区生态 | 文档/Star/更新频率/遇到问题能否搜到答案？ |
| 学习成本 | 团队（自己）多久能上手？ |
| 可替换性 | 未来换掉它的代价多大？（避免深度绑定） |
| 运维成本 | 部署、监控、扩容麻不麻烦？ |

选型原则：**默认选"无聊但成熟"的技术，把新技术的风险留到非关键路径上尝鲜。**

## 🔌 四、接口设计规范（RESTful 为主流基线）

1. **资源用名词复数，动作用 HTTP 动词表达**：
   - `GET /api/v1/guarantees`（列表）、`GET /api/v1/guarantees/{id}`（详情）
   - `POST /api/v1/guarantees`（创建）、`PUT /api/v1/guarantees/{id}`（全量更新）
   - `PATCH /api/v1/guarantees/{id}`（部分更新）、`DELETE /api/v1/guarantees/{id}`（删除）
2. **URL 带版本号**（`/api/v1/...`），破坏性变更升版本，不偷偷改语义。
3. **状态码语义化**：200 成功；400 参数错误；401 未认证；403 无权限；404 不存在；409 冲突；500 服务端错误。禁止"全部 200 + body 里的 code 判错"。
4. **统一响应结构**（团队已有约定则从其约定）：
   ```json
   { "code": 0, "message": "ok", "data": { }, "traceId": "xxx" }
   ```
5. **接口文档先行**：先写接口契约（OpenAPI/Swagger 或 Markdown），评审通过后再编码——下游可并行 Mock 开发。
6. **敏感操作幂等**：支付/退款/创建类接口必须支持幂等键（如 `Idempotency-Key`），防重放重提交。

## 🗄️ 五、数据库设计规范（参考《阿里巴巴 Java 开发手册》数据库规约）

- 表名、字段名**小写下划线**：`guarantee_order`、`created_at`，禁止驼峰与数据库关键字。
- 三必备字段：`id`（主键）、`created_at`、`updated_at`；建议加逻辑删除 `deleted`。
- 字段**NOT NULL + 默认值**优先，避免 NULL 带来的语义二义性。
- 金额用 `DECIMAL`（禁止 FLOAT/DOUBLE）；状态用 `TINYINT` + 字典表/枚举说明，禁止裸魔法数字。
- 单表索引建议 ≤5 个，联合索引区分度高的列在前（最左前缀原则）。
- 大字段（TEXT/BLOB）拆分到扩展表，避免拖慢主表查询。
- 禁止 `SELECT *`；变更 SQL 必须先在测试环境验证并备份。

## 🧾 六、ADR（Architecture Decision Record）——决策留痕

架构上所有"**做过选择**"的地方（框架、存储、中间件、分层方式，以及[方案库](./solution-catalog.md)中方案的取舍）都记一条 ADR，模板见 [ADR模板.md](./adr-template.md)。放在项目 `docs/adr/` 目录，编号递增，**只追加不修改**——决策变了就新增一条并标记替代关系。

## 🧩 七、通用设计方案库（方案货架）

常见场景（幂等、缓存、异步解耦、状态机、对账、RBAC 等 12 类）**先查成熟方案再动手**，每个方案含适用场景 / 标准结构 / 关键要点 / 常见坑：

- 用法：对号入座 → 按图施工 → 裁剪点记 ADR；文末附"交易类 / 内容类 / 中后台 / 第三方对接"四套常用组合，可整包采用。
