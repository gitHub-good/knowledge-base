# 🧾 ADR 模板（Architecture Decision Record）

> 用法：复制本模板到项目 `docs/adr/` 目录，命名 `NNNN-标题.md`（编号递增）。ADR **只追加、不修改**；决策被替代时在文末追加"替代记录"并指向新 ADR。

```markdown
# ADR-NNNN：<决策标题>

- 状态：提议 / 已接受 / 已替代（被 ADR-XXXX 替代）
- 日期：YYYY-MM-DD
- 决策人：（自己 / 相关方）

## 📌 背景
（我们面对什么问题？有什么约束？为什么会需要做这个决策？）

## 🎯 决策
（我们决定怎么做？一句话说清楚。）

## ⚖️ 候选方案对比

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 方案 A | | | ✅ 采用 |
| 方案 B | | | ❌ 否决，原因：… |

## 💡 理由
（为什么选它？对照选型五维度：成熟度/社区/学习成本/可替换性/运维成本。）

## ⚠️ 影响
- 正面影响：
- 负面影响 / 代价：
- 需要跟进的事项：

## 🔍 后续验证方式
（怎么知道这个决策是对的？观察什么指标、什么时间点回顾？）

## ♻️ 替代记录
（若有后续 ADR 替代本决策，在此登记：被 ADR-XXXX 替代，日期，原因。）
```

## 💡 示例：ADR-0001 选用 PostgreSQL 作为主存储

- **状态**：已接受（2026-09-09）
- **背景**：保函平台需要支持事务、复杂查询与 JSON 字段，单人开发，无专职 DBA。
- **决策**：主存储使用 PostgreSQL 16。
- **候选**：MySQL 8（生态成熟但 JSON 与窗口函数体验略弱）/ MongoDB（文档灵活但事务弱）/ PostgreSQL ✅。
- **理由**：事务 + JSONB + 全文检索一站式；社区活跃；被主流云厂商全托管支持，可替换性好。
- **验证方式**：上线 3 个月后回顾慢查询数量与备份恢复演练结果。
