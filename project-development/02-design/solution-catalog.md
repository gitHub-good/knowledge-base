## 🏛️ 一、系统形态

<a id="arch-monolith"></a>

### 🧩 方案 01 · 分层单体 + 前后端分离（默认起点）

**✅ 适用场景**：团队 ≤5 人、业务域单一、追求迭代速度——90% 的内部系统/工具/中小业务。

**🏗️ 标准结构**

```
浏览器 SPA（Vue/React）
   │ HTTPS / JSON
Nginx / 网关（静态资源 + 反向代理 + 限流）
   │
应用单体（四层：接入 → 应用 → 领域 → 基础设施，见 index.md 一）
   │
单数据库（+ Redis 可选）
```

**🔑 关键要点**
- 一切新项目**默认从这里开始**，不为"以后可能"提前上分布式。
- 代码内部按业务域分包（`order/`、`refund/`、`user/`），包之间只走接口——为将来演进留缝。
- 应用无状态，生产**至少 2 个实例** + 负载均衡，获得基本的可用性。

**⚠️ 常见坑**
- 模块间随便互相 import，"伪单体真面条"——用 ArchUnit/依赖检查守住分包边界。
- 多个模块直接读写同一批表，改表牵一发动全身——表归属单一模块。

<a id="arch-evolution"></a>

### 🧩 方案 02 · 架构演进判断（模块化单体 → 微服务）

**✅ 适用场景**：系统长大后的"要不要拆微服务"决策——这是高频错误重灾区。

**⚖️ 拆分判断表**

| 信号 | 说明 |
| --- | --- |
| ✅ 要拆 | 不同模块需要**独立伸缩**（如导出吃 CPU、交易要稳定） |
| ✅ 要拆 | 多团队开发**互相阻塞**（改一处要全员同步发版） |
| ✅ 要拆 | 需要**故障隔离**（一个模块 OOM 拖死全局） |
| ❌ 不拆 | 只是"代码多了"——先做模块化，不动部署 |
| ❌ 不拆 | 为了技术简历——分布式的复杂度由自己买单 |

**🏗️ 演进路线（先逻辑拆，再物理拆）**

```
单体 → 模块化单体（按领域分模块：模块间只走接口 + 各自 schema）
     → 抽离独立模块为服务（每次只拆一个，拆完先跑双写灰度）
     → 微服务（模块数 = 团队结构，不是越多越好）
```

**🔑 关键要点**：每拆一个服务，就多一套部署/监控/链路追踪/分布式事务的成本——**拆是为了解决上面表里的问题，不是为了架构图好看**。

**⚠️ 常见坑**：一步到位大拆分（风险不可控）；拆完共享数据库（伪微服务，耦合还在）。

## 💾 二、数据与存储

<a id="idempotency"></a>

### 🧩 方案 03 · 幂等设计

**✅ 适用场景**：一切写操作（下单、支付、退款、回调），网络重试和用户重复点击**必然发生**。

**🏗️ 标准结构**

```
请求带幂等键（业务单号 / Idempotency-Key）
   → 查幂等记录：已成功？ → 直接返回上次的结果（不是"成功"两个字）
   → INSERT 幂等表（唯一索引）：冲突？ → 并发重复 → 返回处理中/上次结果
   → 执行业务，同事务写入幂等记录与状态
```

**🔑 关键要点**
- 幂等键选**业务语义键**（订单号 + 操作类型），不用随机 UUID——重试时 UUID 变了，等于没防。
- **唯一索引是最后防线**，应用层判重只是快路径，两者都要。
- 幂等记录与业务操作放**同一事务**，防止"判重了但业务没落库"。

**⚠️ 常见坑**：执行到一半失败但幂等记录残留（必须随事务回滚）；前端防抖按钮当幂等用（绕过页面照样重复）。

<a id="cache-aside"></a>

### 🧩 方案 04 · 缓存 Cache-Aside

**✅ 适用场景**：读多写少（配置、商品、字典、热点详情），DB 压力大或 P99 延迟高。

**🏗️ 标准结构**

```
读：查缓存 → 命中返回；未命中 → 查库 → 回填（必带 TTL）
写：先更新 DB → 再删除缓存（不是更新缓存）
```

**🔑 关键要点**
- 默认 **Cache-Aside + 删缓存**；一致性要求更高时用延迟双删或订阅 binlog（canal）异步删。
- **TTL 兜底一切不一致**——任何缓存方案都必须设过期时间。
- 热 key 的 TTL 加随机抖动，防止同一时刻集体过期（雪崩）；不存在的 key 缓存空值 + 短 TTL，防穿透。

**⚠️ 常见坑**：先删缓存再更新 DB——并发读把旧值又填回去（顺序反了）；大 key（一个 key 装整个列表）拖垮序列化与网络——按维度拆 key。

<a id="db-sharding"></a>

### 🧩 方案 05 · 读写分离 / 分库分表 / 深分页

**✅ 适用场景**：单库 CPU、连接数、QPS 到瓶颈；读多写少且能接受毫秒级延迟。

**🏗️ 扩展路线（按代价从小到大）**

```
SQL 与索引优化 → 读写分离（主写从读）→ 按业务拆库 → 分库分表
                                    （一般单表 >2000 万行 或 >5GB 再考虑）
```

**🔑 关键要点**
- 读写分离必须支持**强制主库读**（写后 N 秒内读主库，或关键查询显式标记），否则"改完查不到"。
- 分片键选**查询最高频的维度**（如 `user_id`）；分片键一旦上线几乎不可改，等同重做。
- 非分片键的查询走异构（同步到 ES/宽表），**禁止跨全分片扫表拼结果**。

**📑 深分页**：`LIMIT 100000, 20` 会扫掉前 10 万行——改用**游标分页** `WHERE id > #{lastId} LIMIT 20`，或走搜索引擎。

**⚠️ 常见坑**：跳过分库分表直接上（大多数瓶颈先靠索引解决）；主从延迟未评估就把强一致读放到从库。

## 🛡️ 三、可靠性与异步

<a id="async-mq"></a>

### 🧩 方案 06 · 异步解耦与削峰填谷（MQ）

**✅ 适用场景**：主流程不必同步等待的长耗时步骤（通知、积分、报表、风控复核）；流量脉冲（秒杀、批量导入）。

**🏗️ 标准结构**

```
同步链路只做三件事：参数校验 → 落库（状态=处理中）→ 发消息 → 返回"已受理"
异步消费：幂等消费 → 业务处理 → 更新状态 → 失败进重试队列/死信 + 告警
用户侧：任务中心 / 轮询 / 推送 查询处理结果
```

**🔑 关键要点**
- **先落库再发消息**（本地消息表 / 事务消息），保证"库与消息"一致——只发消息不落库，MQ 丢了没凭据。
- 消费端必须幂等（消息至少投递一次，见 [方案 03](#idempotency)）。
- 同一单据的消息要**串行消费**（按单号哈希到同一队列），防乱序。

**⚠️ 常见坑**：把用户必须马上看到结果的步骤也异步了（体验崩塌）；死信队列没人管——必须配告警与人工处理入口。

<a id="resilience"></a>

### 🧩 方案 07 · 弹性四件套（超时 / 重试 / 熔断 / 降级）

**✅ 适用场景**：**一切**跨进程调用——第三方接口、DB、缓存、MQ，无例外。

**🏗️ 四件套速查**

| 件 | 规则 |
| --- | --- |
| ⏱️ 超时 | 一切调用必设（连接 + 读取）；默认值取该依赖 P99 × 2~3 |
| 🔁 重试 | 只重试**幂等**操作；指数退避 + 随机抖动；≤3 次 |
| 🔌 熔断 | 错误率/慢调用比例超阈值 → 自动快速失败，半开试探恢复（Sentinel/Resilience4j） |
| 🪂 降级 | 兜底预案**预先写好**：默认值 / 缓存旧值 / 简化流程 / 友好报错；开关放配置中心可即时切换 |

**🔑 关键要点**
- **只在最外层重试**：链路三层各重试 3 次 = 最多 27 次放大（重试风暴）。
- **超时要级联收敛**：下游超时之和 < 上游给的超时，否则下游还在忙、上游已判死。

**⚠️ 常见坑**：用框架默认无超时（线程池被慢调用占满）；降级方案"到时候再想"——出事时只剩 500。

<a id="scheduled-job"></a>

### 🧩 方案 08 · 定时任务

**✅ 适用场景**：对账、同步、清理、提醒、报表等周期任务。

**🏗️ 标准结构**

```
调度中心（XXL-Job / K8s CronJob / cron）
   → 分发到执行器（多实例：抢锁 或 调度分片）
   → 幂等执行 + 记录执行流水（开始/结束/处理数/失败数）
   → 失败告警 + 支持手动补跑
```

**🔑 关键要点**
- 任务逻辑**必须幂等**：重复跑一遍结果不变（重跑是常态，不是异常）。
- 多实例部署必须有**抢锁或分片**机制，否则重复执行。
- 大数据量任务**分片并行**，每片记录断点，可续跑。

**⚠️ 常见坑**：单机 cron 直接跑脚本，扩容后静默双跑；全量串行跑超过调度间隔，任务互相追赶把库拖垮。

<a id="reconciliation"></a>

### 🧩 方案 09 · 对账

**✅ 适用场景**：与第三方（支付/银行/渠道）有资金或订单交互的系统——**一致性的最后防线，上线第一天就要有**。

**🏗️ 标准结构**

```
每日定时（方案 08）拉取双方账单
   → 逐笔核对（单号 / 金额 / 状态）
   → 差异分类：单边账（长款/短款）、金额不符、状态不符
   → 差异表登记 + 可自动修复的自动重试（幂等）
   → 剩余差异分级告警 → 人工兜底处理 → 关闭差异单
```

**🔑 关键要点**
- **明细对账，不只对总额**——总额平不代表每笔对。
- 差异要**分类分级并定义处理 SLA**（如单边账当日处理、状态不符 T+1 修复）。
- 修复动作必须幂等且可审计（谁、何时、凭什么修）。

**⚠️ 常见坑**：差异无闭环跟踪，小差异滚成大资损；只对平账不管差异单生命周期。

## 🧰 四、通用业务能力

<a id="state-machine"></a>

### 🧩 方案 10 · 状态机

**✅ 适用场景**：订单、审批、退款等有生命周期、多状态流转的实体。

**🏗️ 标准结构**

```
状态枚举 + 迁移表： (当前状态, 事件) → (新状态, 动作列表)
统一入口：所有变更走状态机组件，禁止旁路 UPDATE
DB 落库：UPDATE t SET status=新 WHERE id=? AND status=旧   ← 乐观并发保证
流水表：who / when / from → to / remark   ← 天然审计日志
```

**🔑 关键要点**
- 迁移表**数据化**（配置/枚举表驱动），不写 if-else 面条——新增流转只加一行。
- 状态变更与业务动作（发消息、记账）**同事务**。
- 以更新影响行数判断并发冲突：`WHERE status=旧` 匹配 0 行 = 已被并发改过，走冲突处理。

**⚠️ 常见坑**：状态字段被多处直接 UPDATE，状态机形同虚设；状态越加越多不评审合并，最后没人说得清。

<a id="rbac"></a>

### 🧩 方案 11 · 认证与 RBAC 授权

**✅ 适用场景**：几乎所有 B 端系统。

**🏗️ 标准结构**

```
认证（你是谁）：登录 → 签发凭证（JWT 短期 1~2h + Refresh Token 续期 / 或 Session）
授权（你能干嘛）：RBAC = 用户 — 角色 — 权限（菜单 / 按钮 / 接口）三层映射
```

**🔑 关键要点**
- JWT 必须**短期 + Refresh Token**；注销/改密用黑名单或直接短过期兜住。
- 权限要**三处核对**：前端隐藏（体验）+ 接口校验（安全）+ **数据权限**（行级：只能看自己组织的数据）。
- 密码用 bcrypt/argon2 加盐；登录接口限流 + 失败锁定（防撞库）。

**⚠️ 常见坑**：把"前端隐藏按钮"当鉴权（接口裸奔）；资源归属不校验——改 URL 里的 id 就能看别人数据（越权是 B 端第一大漏洞）。

<a id="async-task"></a>

### 🧩 方案 12 · 异步任务（大文件导入导出 / 批量处理）

**✅ 适用场景**：Excel 导入导出、报表生成、批量数据处理等耗时 >3 秒的用户操作。

**🏗️ 标准结构**

```
用户提交 → 落任务表（状态=排队，立即返回任务号）
Worker 领取 → 分批流式处理（记录进度 %）→ 产物写对象存储 → 状态=完成
用户：任务中心查看进度/结果 → 下载（失败行可下载原因报表）
```

**🔑 关键要点**
- **一切耗时操作任务化**，绝不占住 HTTP 请求线程（网关超时 + 线程池双杀）。
- 大文件**流式读写**（EasyExcel / POI SAX 模式），禁止整文件载入内存。
- 导入**先全量校验再事务入库**，防止错一半进一半；产物设保留期自动清理。

**⚠️ 常见坑**：同步导出 10 万行把服务打 OOM；任务表状态永远"处理中"（worker 崩溃无兜底）——加超时自动置失败。
