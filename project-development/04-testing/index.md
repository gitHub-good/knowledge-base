# 🧪 04 · 测试规范

> 测试不是"证明我能跑"，而是**用可重复执行的用例固化需求**：01 阶段写的每条 Given/When/Then 验收标准，在这里变成自动化用例。基线：测试金字塔 + AAA + FIRST 原则。

## 📍 阶段定位

- 📥 **上游输入**：[03 编码规范](../03-coding-standards/index.md) 产出并通过 lint 的分支 + 01 阶段的验收标准。
- 📤 **下游输出**：全部用例通过、覆盖率达标的测试报告，作为 [05 代码评审](../05-code-review/index.md) 的提测材料。

## 🔺 一、测试金字塔（业界最流行的分层策略）

```
        ／＼        E2E 端到端测试（~10%）
       ／  ＼       走真实链路，慢而贵，只覆盖核心业务流程
      ／────＼      集成测试（~20%）
     ／      ＼     验证模块间协作：service+数据库、接口层+下游
    ／────────＼    单元测试（~70%）
   ／          ＼   秒级运行、海量覆盖，守住绝大多数逻辑
```

原则：**越往下越多、越快、越稳定**。E2E 失败要能快速定位到下层哪一环。

## 🔬 二、单元测试规范

**AAA 结构（每条用例必备三段）：**

```python
def test_partial_refund_over_amount_should_reject():
    # Arrange 准备：构造数据与环境
    order = Order(paid=1000)
    # Act 执行：调用被测行为（一次只测一个行为）
    result = refund(order, amount=1500)
    # Assert 断言：验证结果（含异常场景）
    assert result.rejected is True
    assert "超出可退金额" in result.message
```

**FIRST 原则：**

| 原则 | 含义 |
| --- | --- |
| Fast 快 | 全量单测分钟级跑完，否则没人愿意跑 |
| Independent 独立 | 用例之间零依赖、可任意顺序执行 |
| Repeatable 可重复 | 任何环境结果一致（时间/随机数要 mock 或固定种子） |
| Self-validating 自校验 | 断言自动判成败，禁止靠人眼看输出 |
| Timely 及时 | 与实现同时写（测试先行 TDD 更佳） |

细则：
- **命名即文档**：`test_<方法>_<场景>_<期望>`，如 `test_refund_over_limit_should_throw`。
- **一次只测一个行为**；一个断言关注点（一条用例可多断言，但都围绕同一行为）。
- **mock 边界**：只 mock 外部依赖（网络/DB/时钟），不 mock 被测类内部方法——mock 过度会让测试只会"重播实现"。
- 测试代码也是代码：遵守 [03 编码规范](../03-coding-standards/index.md)，可读、无重复（公共构造抽 fixture/factory）。

## 📊 三、覆盖率标准（业界常用阈值，作为门禁而非目标）

| 口径 | 阈值 |
| --- | --- |
| 新增代码行覆盖率 | ≥80%（合入门禁） |
| 核心模块（领域层/资金/支付） | ≥90% |
| 全仓整体 | ≥60% 起步，逐步抬升 |

> 覆盖率是**底线指标不是质量指标**：100% 覆盖但断言空洞 = 自欺。追求的是"每个分支都有用例表达意图"。

## 🧮 四、测试范围矩阵（提测前自查）

| 维度 | 必测项 |
| --- | --- |
| 主路径 | 每条验收标准至少 1 条正向用例 |
| 边界值 | 0、1、最大值、空集合、刚好超限 |
| 异常路径 | 依赖超时、下游返回错误、非法参数、并发重复提交 |
| 数据一致性 | 事务回滚后数据状态、幂等重试结果 |
| 兼容性 | 接口变更对旧调用方的影响（破坏性变更见 02 的版本规范） |
| 安全 | 越权访问（A 用户操作 B 用户资源）、SQL 注入、敏感信息不落日志 |

## 🔁 五、回归与冒烟

- **冒烟测试集**：≤20 条、10 分钟内跑完、覆盖"上线即崩会死人"的核心链路；每次部署后必跑。
- **回归策略**：自动化回归跑全量单测+集成；改动范围内的 E2E 必重跑；与本模块有调用关系的模块按影响面圈选。
- 修 bug 先补测试：**每个缺陷修复必须附带一条能复现该缺陷的失败用例**（修前红、修后绿），否则修复不算完成——这是缺陷不再复发的前提。

## 🐞 六、缺陷管理

**严重等级定义：**

| 等级 | 定义 | 响应要求 |
| --- | --- | --- |
| P0 致命 | 主流程不可用 / 资金错误 / 数据丢失 | 立即响应：最小修复 + 补回归用例 + 精简评审，修完合回主干 |
| P1 严重 | 核心功能异常但有绕行方案 | 24h 内修复 |
| P2 一般 | 次要功能异常 | 本迭代内修复 |
| P3 轻微 | 体验/文案问题 | 排期修复 |

**缺陷生命周期：** `新建 → 确认（定级/定位）→ 修复 → 验证 → 关闭`；无法复现的挂起并注明复现步骤缺口，不许直接关闭。
