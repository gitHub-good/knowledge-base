# 👀 05 · 代码评审（Code Review）

> 评审的三大价值：**挡缺陷、传知识、保一致**（基线：Google《How to do a code review》工程实践）。评审不是挑刺，是第二双眼睛。

## 📍 阶段定位

- 📥 **上游输入**：通过 [04 测试规范](/project-development/04-testing/index.md) 自查、lint 全绿的 PR。
- 📤 **下游输出**：评审通过（approve）并合入主干的代码——链路收口。

<a id="review-process"></a>

## ⏱️ 一、流程与时效

| 环节 | 规范 |
| --- | --- |
| PR 大小 | ≤400 行 diff（Google 统计：超过 200~400 行，评审发现率骤降） |
| 首次响应 | ≤24 小时给出首轮意见（Google 基线） |
| 评审轮次 | ≤2 轮为宜；反复 3 轮以上说明事先没对齐，应转线下讨论 |
| 合并条件 | 评审意见全部 resolved + ≥1 人 approve + CI 全绿 |
| 分支寿命 | feature 分支 ≤3 天，小步快跑，别攒"大件" |

**单人项目的替代方案（隔天自评）**：睡一觉之后、切上下文之前，以"读别人代码"的心态 review 自己的完整 diff，按下面的清单逐项过——心理距离产生评审效果。

## 🔍 二、评审清单（按优先级排序）

**1. 🎯 正确性（最优先）**
- [ ] 逻辑与验收标准一致，边界条件处理正确
- [ ] 并发/幂等：重复提交、乱序回调是否安全
- [ ] 资源释放：连接、文件句柄、锁
- [ ] 失败路径：下游挂了会发生什么（超时、重试、降级）

**2. 📖 可读性与可维护性**
- [ ] 命名是否达意，他人无需作者讲解能看懂
- [ ] 是否有不必要的复杂度（过度设计、无用的抽象）
- [ ] 与代码库既有风格一致（不要在同一个 PR 里"顺手"重定义风格）

**3. 🧪 测试**
- [ ] 新逻辑有对应测试；缺陷修复有回归用例
- [ ] 断言有效（不是恒真断言）

**4. 🛡️ 安全**
- [ ] 越权校验、输入校验、SQL 注入/XSS
- [ ] 密钥/敏感信息未硬编码、未落日志

**5. ⚡ 性能（有疑点才深究，别过早优化）**
- [ ] 循环内是否有 N+1 查询、重复计算
- [ ] 大数据量场景是否需要分页/限流

## 🤝 三、评审礼仪（同样适用于别人评你的代码）

**评审人：**
- 对事不对人：说"这段循环在并发下可能丢数据"，不说"这写得也太差了"。
- 区分严重级别：`[blocker]`（必须改）vs `[suggestion]`（建议，作者可拒绝并说明理由）vs `[question]`（提问澄清）。
- 给方案不只给问题：最好附上替代写法或文档链接。
- 不吹毛求疵：纯格式问题指给工具（lint/formatter），不要刷屏。

**作者：**
- PR 描述写清楚"做什么/为什么/怎么测"，别让评审人考古。
- 每个 comment 都要回应：改了就说 done；不认同就摆理由，不许"已读不回"。
- 大改动先发设计（见 [02 设计架构](/project-development/02-design/index.md)），评审不是用来否决方案的。

## ⛔ 四、常见否决点（blocker 速查）

1. 无测试或测试无效的新逻辑
2. 吞异常 / 静默失败
3. 硬编码密钥、内网地址、魔法数字
4. 破坏性接口变更未升版本、未通知调用方
5. 明显的注入/越权风险
6. PR 混入了大量无关改动（要求拆分）

<a id="dod"></a>

## ✅ 阶段检查清单（DoD）

- [ ] PR ≤400 行、描述完整、关联需求编号
- [ ] 全部评审意见 resolved，≥1 人 approve
- [ ] 隔天自评（单人项目）已完成
- [ ] CI 全绿（lint/构建/测试/覆盖率门禁）
- [ ] Squash 合入主干，分支即删——链路收口
